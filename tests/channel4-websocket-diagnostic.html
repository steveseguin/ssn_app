Channel 4 WebSocket Diagnostic

A standalone listener and routing check for Social Stream Ninja. It connects directly to wss://io.socialstream.ninja/join/[session]/4, displays every frame without filtering, and prepares a report that can be copied to support.

Before starting

  1. Run the Social Stream Ninja Desktop App and make sure its main capture switch is on.
  2. Under Global settings → Mechanics, enable Enable remote API control of extension and Send chat messages to API server (for external listeners).
  3. For this public-server test, Local Server must be off. The File menu should say Enable Local Server, and generated links must not contain localserver.
  4. Paste the Session ID—or a generated dock URL containing it—below, then click Connect.
  5. Click Arm app test, then immediately click Trigger a fake test message inside the Desktop App.
An open WebSocket only proves that this browser reached the server. It does not prove that the Desktop App publisher joined the same session. The independent routing self-test below separates those two cases.

How to interpret the results
Result Meaning
App test passes and routing test passes The public channel-4 path is working end to end.
Routing passes, app test receives nothing The listener and server route work. The Desktop App is not publishing to this session/channel. Fully quit and restart it after setting the Session ID, then retry.
Socket opens, but routing test times out The handshake succeeded, but a message could not cross channel 4 for this session. Recheck the exact Session ID and send the report to support.
Connection fails or closes with code 1006 A network, TLS, proxy, firewall, antivirus, or server connection problem is possible. Browsers usually hide the detailed reason, so include the report and browser console output.
